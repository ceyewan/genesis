# Genesis 核心场景示例设计

> 本文是场景型示例的设计总览。除特别标记为“已实现”的场景外，其余内容只描述
> 计划验证的链路和组件边界，不代表仓库已经提供对应实现。

Genesis 现有示例主要按组件拆分，适合学习单个包的构造方式和 API。场景型示例解决
另一个问题：在一条接近真实业务的链路中，应该把哪些组件放在哪里，它们如何协作，
以及出现重复请求、突发流量、下游故障或重复消息时系统应该表现成什么样。

场景示例不会追求把所有组件塞进同一个工程。每个场景只围绕一个核心工程问题组合
必要组件，并提供可以自动验证的成功路径和故障路径。

## 场景总览

| 场景 | 核心问题 | 主要组件 | 状态 |
| :--- | :--- | :--- | :--- |
| 全链路可观测性 | 如何看清跨 HTTP、gRPC、DB、MQ 的一次请求 | `clog`、`metrics`、`trace`、`db`、`mq` | 已实现 |
| Web 与 RPC 弹性保护 | 如何处理突发流量、重复提交和下游故障 | `ratelimit`、`idem`、`breaker` | MVP 已实现 |
| 可靠异步任务 | 如何面对至少一次投递、重复消费和临时失败 | `mq`、`idem` | MVP 已实现 |
| 缓存化数据查询 | 如何组合缓存、数据库和缓存重建保护 | `cache`、`db`、`dlock` | MVP 已实现 |
| gRPC 服务发现与调用治理 | 如何发现实例、建立调用并隔离故障 | `registry`、`breaker`、`connector` | MVP 已实现 |

`config`、`clog`、`xerrors` 是这些场景的基础能力；`metrics` 和 `trace` 可以按场景需要
接入，但只有可观测性场景负责展示完整的采集与查询后端。

## 场景一：全链路可观测性

### 目标

回答“一次请求经过了哪些服务、慢在哪里、失败在哪里，以及如何用日志补充业务细节”。
这个场景是其他场景的可观测性参考实现，不承担流量治理或一致性教学。

### 链路

```text
HTTP Gateway → gRPC Logic → SQLite → NATS JetStream → Task → gRPC Callback
```

### 验证重点

- HTTP、gRPC 和 MQ 之间的 TraceContext 能正确传播。
- Prometheus 能抓取服务与 MQ 指标。
- Loki 能按 `trace_id` 关联多个服务的日志。
- Tempo 能展示跨同步和异步边界的完整链路。

### 当前实现

参见 [`examples/observability`](../observability/)。该示例已经包含 Docker Compose、
Grafana、Prometheus、Loki、Tempo、压测脚本和自动验收脚本。

## 场景二：Web 与 RPC 弹性保护

### 目标

回答三个常见问题：入口流量过大怎么办、客户端重复提交怎么办、下游 gRPC 服务持续
失败怎么办。

### 链路

```text
POST /orders → RateLimit → Idempotency → Gateway Handler
                                         ↓
                                  gRPC Client Breaker
                                         ↓
                                    Inventory Service
```

### 组件职责

- `ratelimit` 位于 HTTP 或 gRPC 服务端入口，拒绝超过配额的请求。
- `idem` 位于认证和限流之后，复用相同业务请求的成功结果。
- `breaker` 位于 gRPC 客户端，按稳定、低基数的服务或方法 key 隔离系统性故障。
- 调用超时由 `context` 控制，不能用 breaker 代替。

### 验证重点

- 相同幂等 key 的并发请求只成功执行业务一次，并获得一致结果。
- 突发流量会产生明确的 `429`，窗口恢复后请求重新通过。
- 下游持续返回 `Unavailable` 后 breaker 打开，调用快速失败且不再到达下游。
- 库存不足等业务错误不会被统计为熔断故障。
- 冷却结束后，半开探测可以使调用链恢复。

### 详细设计

参见 [`examples/resilient-service`](../resilient-service/)。第一版保持两个逻辑服务和一个
Redis 依赖，不重复搭建可观测性示例的完整后端。

## 场景三：可靠异步任务

### 目标

回答“消息可能重复投递、处理过程可能临时失败时，消费者如何安全重试”。这个场景
重点解释 at-least-once 投递与幂等消费的配合，不承诺 exactly-once。

### 链路

```text
HTTP Submit Task → MQ Publish
                    ↓
            Worker + Idempotent Consume
                    ↓
            Ack / Retry / Terminal Error
```

### 组件职责

- 生产调用方生成稳定任务 ID，并作为消息和幂等处理的关联标识。
- `mq` 负责持久化投递、manual ack、队列组和有限重试。
- `idem.Consume` 使用业务任务 ID 去重，避免同一成功任务被重复处理。
- `clog`、`trace` 和 MQ 自带指标用于观察发布、消费、重试与最终失败。

### 验证重点

- 同一消息被重复投递时，业务副作用只成功执行一次。
- 临时错误不 ack，消息经过有限次数重试后成功。
- 永久业务错误不会无限重试，应进入明确的终止或补偿路径。
- 多个 Worker 使用 queue group 时，同一次投递只由一个实例处理。
- Worker 在处理期间退出后，未确认消息能够被其他实例重新处理。

### 边界

该场景不把幂等组件描述成事务系统。业务存储仍需要唯一约束或条件更新作为最终防线；
消息发布和数据库事务的一致性属于 outbox 等更高层方案，不在第一版示例中假装解决。

## 场景四：缓存化数据查询

### 目标

回答“读多写少的接口如何组合本地/分布式缓存与数据库，以及热点 key 失效时如何避免
大量请求同时回源”。

### 链路

```text
GET /products/:id → Cache Lookup → Hit → Response
                           ↓ Miss
                    DLock Rebuild Guard
                           ↓
                      Database Query
                           ↓
                       Cache Fill
```

### 组件职责

- `cache` 负责结果读取、写入和 TTL；是否使用 Local、Distributed 或 Multi 由示例配置
  明确决定，不能把不同模式描述成完全相同。
- `db` 是权威数据源，并借用应用层创建的数据库 connector。
- `dlock` 只保护热点 key 的缓存重建，不把分布式锁当作数据库事务。
- `xerrors` 统一区分 cache miss、记录不存在和基础设施错误。

### 验证重点

- 缓存命中不会访问数据库。
- 缓存未命中时读取数据库并回填，后续请求命中缓存。
- 多个并发请求遇到同一热点 key miss 时，只有锁持有者执行重建。
- 锁等待者在锁释放后重新检查缓存，而不是直接再次查询数据库。
- 数据库记录不存在时使用短期负缓存或显式空值策略，避免穿透；该策略必须在示例中
  明确，而不是藏在组件内部。

### 边界

第一版只演示 cache-aside，不承诺缓存与数据库强一致。写后失效、双删、CDC 和跨服务
缓存一致性应作为后续专题，而不是混入基础读取案例。

## 场景五：gRPC 服务发现与调用治理

### 目标

回答“调用方如何发现多个 gRPC 实例，并在实例变化和服务故障时保持可控调用”。这个
场景专注 gRPC 客户端基础设施，不重复 Web 入口治理。

### 链路

```text
Service Instances → Registry
                       ↓ Discover / Watch
Caller → gRPC Resolver → Client Connection → Breaker → Service Instance
```

### 组件职责

- `registry` 负责服务注册、发现和实例变化观察。
- `connector` 或应用层连接管理负责底层客户端资源和关闭顺序。
- `breaker` 隔离服务级或方法级系统故障，但不承担实例摘除和负载均衡职责。
- `trace` 传播跨服务上下文，`clog` 记录实例变化和调用错误。

### 验证重点

- 启动多个服务实例后，调用方能够发现并调用它们。
- 新实例加入或旧实例退出后，调用方最终看到更新后的实例集合。
- 单个实例退出不会使整个调用方永久不可用。
- 系统性 gRPC 错误可以触发 breaker；稳定业务错误不会触发。
- 注册、watch、gRPC 连接和 breaker 的生命周期由创建者按逆序关闭。

### 边界

服务发现、负载均衡和熔断是三件不同的事。示例应明确底层 gRPC resolver/balancer 的
行为，不把 `registry` 描述成完整的服务网格，也不承诺瞬时一致的实例视图。

## 实施顺序建议

建议按以下顺序推进：

1. 保持现有全链路可观测性案例，并将它作为场景型示例的质量基线。
2. 实现 Web 与 RPC 弹性保护，先覆盖最常见的同步请求链路。
3. 实现可靠异步任务，补齐 MQ 的生产级组合方式。
4. 实现缓存化数据查询，集中讲解数据访问与缓存重建边界。
5. 最后实现 gRPC 服务发现与调用治理，因为它涉及 resolver、实例变化和生命周期，
   更适合作为进阶场景。

每个可运行场景最终都应提供：架构说明、一键启动方式、正常路径、故障注入方式、自动
验收脚本、资源关闭顺序，以及“当前没有解决什么”的边界说明。
