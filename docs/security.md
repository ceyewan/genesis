# 安全与依赖治理

## 漏洞扫描

CI 当前未运行 `govulncheck`，因此不能声明“无已知可达漏洞”。`go mod verify` 只验证
依赖内容与校验和，不等同于漏洞扫描。

发布前运行 `make vulncheck`，使用 `Makefile` 固定版本的 `govulncheck` 扫描全仓源码，
默认访问 `https://vuln.go.dev` 并发送模块/包元数据。联网扫描须得到维护者同意；
也可使用离线或组织管理的漏洞数据库，记录扫描工具、数据库日期及发现处置。

逐项审阅生产组件和测试基础设施的可达性报告；静态扫描的调用链不等同于已证实可利用，
但存在未处置的生产安全问题时不能发布。例外必须记录原因、暴露范围、缓解措施和复审日期。

使用 Go 的最新安全补丁构建和扫描；仅以最低可编译版本通过测试不能证明安全。
不能把未扫描、扫描失败或 JSON 输出模式的零退出码解释为没有漏洞。
未经同意不新增外部扫描服务。

## 依赖完整性与更新

- 审阅 `go.mod` / `go.sum`；CI 检查 `go mod verify` 和 `go mod tidy` 漂移。
- 工具和依赖的固定版本以仓库配置为准，不另维护版本清单。
- Patch/minor 更新运行普通、race、lint、API、文档和相关场景测试。
- 上游 major 升级或投递、TTL、编码、租约等语义变化，需契约审阅与迁移说明。
- 已知被利用或严重可达漏洞优先处理；无法立即修复时记录暴露范围、缓解措施和例外期限。

公共 API 暴露上游类型时，不能只以编译通过证明兼容。具体支持范围见
[兼容性说明](./compatibility.md)，发布步骤见[发布流程](./release.md)。

应用安全责任集中在[生产接入](./production.md)，组件配置限制查各包 GoDoc。
