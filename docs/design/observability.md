# 可观测性

## 为什么接受进程级 provider

OTel 中间件、数据库插件和第三方埋点往往读取全局 provider。统一安装可以让这些
库共享同一套导出和传播配置，不必为每个适配层增加注入选项；代价是同进程多套
隔离实例更难组合，重复初始化也有全局副作用。

Genesis 保留这一选择，但不把初始化伪装成普通局部工厂。应用负责 bootstrap 与
退出；库内部不自行创建生产 provider。隔离测试也必须考虑进程级状态。

## 异步消息为什么默认使用 link

消息可能延迟消费、重投、被多个消费者处理或参与批处理。这些关系不总是一次
同步调用的继续，强行使用 parent/child 会把因果关联误画成一条线性请求生命周期。
Link 保留生产与消费的关联，同时让消费拥有自己的 trace；确实需要线性关系时，
调用方再显式选择。接入代码见[可观测性示例](../../examples/observability/README.md)。

## 统一字段是给消费端的约束

稳定的资源字段、错误结构和指标标签让查询与告警可以跨服务复用。
如果同一个含义在每个服务里都换一个名字，调用端少写的代码会变成平台侧长期的
兼容负担。标签自由度也有成本：任意 URL、用户 ID 或请求 ID 会放大时序基数。

日志、指标和 trace 不需要合成一个大组件。通过上下文和稳定标识关联它们，既能
保留各自采样、存储和检索方式，也避免把 Genesis 绑定到某个观测后端。

## 日志不接管退出流程

日志层退出进程会跳过应用的清理顺序，并使组件和测试无法掌握控制流。
因此严重程度与退出决策分开：日志表达事件，应用决定是否停机、如何关闭资源。
