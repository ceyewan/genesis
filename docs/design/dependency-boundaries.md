# 依赖与能力边界

## 为什么不隐藏所有第三方类型

Connector 管连接生命周期，不再包一套 Redis、Etcd 或 Kafka 命令；DB 保留 GORM
查询能力。如果把每个上游方法翻译成 Genesis 接口，要么长期追赶完整 SDK，要么
迫使调用方频繁绕过不完整的封装。高级能力直接使用原生类型，是接受依赖绑定来
避免假解耦；相应的上游 major 升级必须纳入 Genesis 的兼容性审阅。

`clog` 使用标准库字段类型，`xerrors` 保留标准库错误链，理由相同。它们统一工程
约定，但不另造日志数据模型或协议错误系统。HTTP/gRPC 的错误映射仍属于应用边界。

## 为什么配置加载不负责重新装配

加载配置与替换活跃组件是两个问题。连接器、锁租约和正在处理的请求不能随着一个
文件变更无条件重建，否则会产生资源重叠、请求中断和部分更新。
Genesis 提供变更通知，把验证、替换及旧实例释放的顺序留给应用。

配置源也不扩成通用远程配置中心：认证、离线缓存、版本回滚与分布式一致性会带来
另一套生命周期和运维要求，不应藏进一个基础加载器。

## 为什么缓存不做统一数据结构 SDK

本地热点缓存与 Redis 结构化存储解决的成本问题不同。把 Hash、Sorted Set 等能力
强加给本地和多级缓存，会让字段回填、局部失效与冲突处理成为隐含的一致性协议。
Genesis 只共享必要的 KV 能力，接受 Redis 扩展不是跨后端可移植接口。

## 为什么数据库组件不承诺透明分片

分片涉及路由、物理表管理、跨分片事务和主键分配，不能靠一个初始化选项完整表达。
这些决策属于应用的数据架构；数据库原生分区与跨库分片也不能视为同一能力。
Genesis 不为减少几行查询代码而承诺透明的数据迁移与一致性。
