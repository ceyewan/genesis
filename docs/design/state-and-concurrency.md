# 状态与并发

## 多级缓存选择延迟，而不是同步镜像

跨实例本地失效需要广播、重试与消息丢失恢复；严格跟随远端剩余 TTL 还需要额外的
读取和竞态处理。这会把一个读加速策略变成分布式一致性协议。
Multi 接受陈旧窗口，不把它包装成强一致缓存。

同实例的迟到回填是不同问题：它不能覆盖已经完成的写入或删除。协调读写可以解决
这个范围内的竞态，但会增加快路径同步成本并让不同 key 竞争；等待必须允许取消。
相关成本与测量限制见[性能测试](../performance.md)，具体语义见[cache](../../cache/README.md)。

## 租约不能替业务存储隔离旧持有者

续期降低正常长任务丢锁的概率，却无法阻止一个暂停后恢复的旧进程继续写下游。
因此锁的所有权检查与数据库的唯一约束、版本/CAS 是不同的防线。
Genesis 不把“自动续期”提升为对任意外部副作用的互斥保证。

Redis 与 Etcd 的租约模型和时间精度不同；统一入口不值得以静默舍入 TTL 或
隐藏所有权变化为代价。后端差异留在各组件 GoDoc，而不是伪装成可随意互换的协议。

## 幂等复用不是跨存储事务

业务副作用成功与去重结果写入之间可能发生崩溃。只要这两件事不在同一个事务里，
应用层幂等就无法证明 exactly-once。缓存成功结果能减少重放，但不能替代持久化约束。

结果大小与 key 数量也必须有边界。拒绝或不缓存超限结果会影响重放行为，却比接受
任意客户端输入、无界占用内存更可控；业务不能把有限缓存当作永久处理记录。

## ID 能力为什么分开

Snowflake、UUID、按业务键递增的序列、WorkerID 分配不是同一个需求。强行统一会让
只需要一个字符串 ID 的调用方也承担时钟、节点编号与租约管理。

位布局是持久化协议，因此机房与 WorkerID 的分配模式应显式选择，不能根据某个
字段是否为零猜测。时钟回拨和序列耗尽宁可返回错误，也不返回可能碰撞的“备用 ID”。
