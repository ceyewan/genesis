# 服务调用治理

## 无状态 JWT 的收益与代价

本地校验避免每个请求查会话存储，也减少认证链路的外部依赖。代价是撤销、并发
刷新和 refresh token 重放检测不能靠签名校验解决。需要强会话控制的系统应引入
持久化会话或身份平台，而不是把长期 JWT 当作完整登录体系。

## 入口保护与依赖故障是两种判断

令牌桶允许有限突发，适合入口资源保护；为支持多种算法而增加统一配置面，会让
简单的放行判断承担复杂配额系统的职责。限流器故障时放行还是拒绝，没有通用答案：
可用性保护与防刷、成本保护的优先级不同，必须让应用显式选择。

熔断则判断依赖是否持续不可靠。若把业务拒绝也记成系统故障，大量合法业务错误
可能打开熔断器并阻断健康流量。隔离域过粗会误伤，过细又会稀释故障样本并增加
状态基数；选择服务级还是方法级应依据真实故障分布，而不是客户端可控的请求 ID。

## 服务发现不承担完整服务网格

Registry 接入 gRPC resolver，使地址变化交给 gRPC 连接和负载均衡处理。
限制 endpoint 的协议范围，是为了避免存储层允许任意地址、连接层却无法解释它们。

进程级 resolver 注册让简单部署少一层实例路由配置，也限制了同进程的独立 Registry
组合。这是当前约束，不是支持任意多租户发现域的承诺。

Watch 在历史 revision 被 compact 后只能根据最新快照恢复状态，无法还原所有中间
事件。面向最终地址集的恢复，比宣称“不丢事件”更符合服务发现需要。

## 消息系统统一接入，不统一后端协议

JetStream 与 Redis Stream 的确认、重投和消费身份不同。统一中间件可以复用重试、
日志与恢复逻辑，但不能创造后端不存在的能力。实例本地预取和共享消费者背压也
不是同一个预算；把它们混为一个选项会让多副本部署相互干扰。

业务重试分类与死信处置留给应用，因为永久失败的判断、有效载荷和目标 topic
属于业务协议。关闭与排空分开，则是为了让应用选择有限等待或立即停止，不能据
“已返回关闭”推断忽略 context 的业务处理已经被 Go 强制终止。
