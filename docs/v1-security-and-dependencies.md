# 安全与依赖治理

本文是现行政策。旧 RC2 的扫描豁免、指定下游验收和证据归档协议只属于历史记录，
不是当前发布门禁。发布操作以[发布流程](./release.md)为准。

## 漏洞扫描

CI 当前未运行 `govulncheck`，因此不能声明“无已知可达漏洞”。`go mod verify` 只验证
依赖内容与校验和，不等同于漏洞扫描。

稳定 v1 发布前，维护者应明确选择并记录以下一种方式：

- 使用固定版本 `govulncheck`，允许向选定数据库发送模块/包元数据，逐项审阅可达性。
- 使用离线或组织管理的漏洞数据库，记录扫描工具、数据库日期及发现处置。
- 明确接受未提供可达性扫描的风险，说明原因、缓解措施和复审日期。

未经同意不新增外部扫描服务。不能把未扫描或扫描失败解释为没有漏洞。

## 依赖完整性

- 审阅 `go.mod` / `go.sum`；CI 检查 `go mod verify` 和 `go mod tidy` 漂移。
- Go、质量工具和 GitHub Actions 版本以 CI 固定值为准，见[兼容矩阵](./v1-compatibility.md)。
- 不移动或覆盖已发布标签。依赖更新通过单独 PR 合入，并发布新版本。
- 发布后在隔离缓存、`GOWORK=off` 环境验证公开模块可下载，不依赖本地源码替换。

## 升级与例外

Patch/minor 更新运行普通、race、lint、API、文档和相关场景测试。公开接口暴露的
第三方类型需要额外兼容性审阅；不能只以编译通过证明语义兼容。

上游 major 升级，或消息投递、TTL、编码、租约等语义变化，需要明确契约与迁移说明。
已知被利用或严重可达漏洞优先处理；无法立即修复时记录暴露范围、缓解措施和例外期限。

Genesis 不以某个指定下游仓库作为发布前置条件。应用维护者自行进行升级与业务验收。
CI 不自动发布，不新增个人令牌、发布哈希链或固定数量的 Release 资产协议。

## 应用安全边界

应用负责凭证管理、TLS、网络访问控制、身份作用域、持久化和备份。开发示例中的
明文连接、调试接口及内存状态不能直接作为生产安全配置。组件的默认值和限制见各包
README，幂等与互斥不能替代数据库唯一约束或 CAS。
